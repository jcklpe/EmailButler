## Prepare compatibility, backups and the candidate
1. For a source update, fetch the intended upstream release/default branch through existing authorized Git tools and prepare an isolated source candidate. Registration-only migration of an already suitable package keeps the source unchanged and skips fetching/upgrading it. Never reset, clean, overwrite, auto-stash or publish local customizations. Compare customizations with their original upstream baseline and deliberately carry them into the candidate; keep private state and recovery copies outside source checkouts.
2. Compare the installed readers, record contracts and storage pointers with the target's. Prepare an exact per-store plan: preserve in place, copy to a required new location, convert with a tested mapping, or stop for an unsupported/ambiguous format. Keep compatible state in place. Moving folders for branding is unnecessary. Unknown locations or meanings require resolving the gap before activation; a generic file copy is not proof that the target can use the data.
3. Before changing live files, coordinate a stable snapshot with actual writers. Prepare a private recovery set containing persistent state, source/customization baseline, registrations and relevant nonsecret host pointers. Verify copied bytes and private access permissions, then restore the backup into separate private scratch and check it with the installed readers. Keep secrets and connection credentials out of source, migration fixtures and this recovery set. A Git revision alone does not back up uncommitted customizations or private state. Never delete an unknown lock to force a snapshot.
4. Prepare converted state in a separate private working copy. Use an applicable released migration or prepare a bounded converter from understood source/target contracts, testing it on synthetic fixtures and the private copy before proposing activation. Preserve effective settings, historical identities/integrity links, recorded outcomes and exact unfinished work. Preserve pending proposals as pending; prior approval receipts never authorize conversion-time activation or mailbox writes. If a format or integrity binding cannot be handled faithfully, leave the current installation usable and explain the compatibility gap.
5. Before activation, run the candidate's `skills/setup-emailbutler/scripts/run_tests.py`, skill validation and package link/resource checks. Use the target's readers with the explicitly selected private copy to verify every relevant store and its relationships, including resume/history inspection without replaying actions. Require the backup-restoration checks above as well as target parsing. A registration-only change still checks target readability and preserves a recovery baseline. The [migration checklist](references/migration.md#verification-before-activation) defines the evidence required; missing checks block activation of affected changes.
6. Show a short readable plan covering relevant behavior, private-data moves/conversions, local customizations, recovery and any real compatibility choice. Obtain agreement for the exact candidate and migration unless already approved within scope. Preserve the user's chosen preferences; migration does not authorize new defaults, connectors, scopes, mailbox operations or data deletion.

## Activate the verified plan
Recheck source, state and host-pointer baselines against the tested snapshot before writing. If anything changed, preserve the newer work and prepare a fresh consistent snapshot/candidate. Keep relevant writers quiescent through cutover. Activate the checked source, private-state location/format, host pointers and registrations as one coordinated plan; do not let a client run a new reader against unprepared state. This workflow decides whether existing registrations need migration. Invoke `skills/setup-emailbutler/scripts/install_skill.py` from the approved final checkout, not a disposable instruction candidate. Preview `--migrate-registrations` for the selected clients and confirm its concrete paths match the reviewed plan; only then add `--execute` within the approved scope. Conflicting/copied installations remain intact. See [registration mechanics](references/migration.md#registration-mechanics).

## Verify the active installation or recover
Read back the installed package, registrations and actual host state-location pointer. Use its readers to inspect preserved settings, history and pending progress without modifying mail or applying proposals. Check active client discovery/reload through supported controls, and distinguish saved files from verified active behavior. Explain a required new chat or app confirmation in ordinary terms. Onboarding remains unknown when evidence is absent; an update never starts a surprise cleanup.

On failure, use the tested recovery set to restore the matching source, state, pointers and registrations within scope. Check for writes since cutover before restoring data: preserve newer work and both versions if a direct restore would discard it, then resolve recovery deliberately. Reverting code alone may leave migrated data unreadable. Retain verified backups until cleanup is explicitly authorized; leave one identified active state location and avoid divergent active copies. Report the verified result, any unavailable history/progress and any remaining activation or recovery gap. For a setup handoff, return to Setup only for the still-requested connection checks and first-run work.
