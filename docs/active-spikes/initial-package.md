# Initial package
EmailButler is an agent-operated Gmail/Outlook assistant distributed as one package of focused skills with shared helpers and contracts. Existing connectors are the initial access route. No custom Google OAuth project, hosted mailbox bridge, or external toolkit is part of this scope.

## Adopted product requirements
Provide a useful initial preview before asking a long set of preference questions. Keep account coverage and meaningful limitations visible while handling technical details for the user. Use native labels, categories, and mailbox rules for predictable work. Require the direct-user phrase “change my email butler” to begin changes to durable behavior, with typed proposals, conversational confirmation of the displayed preview, and rollback of local configuration. Technical hashes remain internal; short B labels distinguish alternatives when necessary.

## Initial implementation scope
Bundle Git-based recipient onboarding and local skill registration, a tool-inventory capability check, a strict private-profile writer, synthetic tests, and documentation pointers for recipient-side capability checks. Typed changes cover preferences, organization plans, rule plans, workflow revision requests, access change requests, and configuration restore. Workflow/access requests remain proposals until the separate implementation/authorization route is completed. Scripts do not call mail APIs or carry credentials.

## Distribution and setup
The public Git repository is the sole distribution route. The user copy-pastes the README prompt into their own agent, which retrieves the repository, installs the skill, installs/enables requested official connectors, and verifies that environment. Sign-in, consent, and required approvals stay with the user. Work-laptop restrictions are addressed when observed. No archive/upload path is maintained. Development-account inspection is not recipient acceptance evidence.

## State and verification
Keep user state outside source/distribution. Native rules remain canonical in the mailbox; a local rule plan does not prove installation. A script can validate structure and limits, but cannot authenticate the human origin of a CLI argument, judge whether a rule is wise, enforce the host's tools, or prevent an agent from bypassing files it can edit. Those limits must be explicit.

## Review, memory, and volume reduction
The chat review uses stable numbered blocks, defaults to 15 messages in total for text and two or three in voice, and saves a private resumable queue. A queue records completion/deferral without carrying approvals into a new chat. Settings history is reconstructed from immutable proposals and saved profile revisions. A separate typed journal holds confirmed action receipts and clear feedback; it counts distinct messages and never edits policy. Local state survives fresh sessions using the same directory; shared cloud/local persistence still requires an adapter.

The organization workflow proactively checks completed slates and surfaces at most one worthwhile keep-receiving, unsubscribe, or narrow-native-rule discussion per session. First-run quick sorting proposes a small filing scheme and approved high-volume groups. Stars, flags, and habitual Inbox storage inform destinations without creating automatic Inbox exemptions; explicit user overrides remain authoritative. Inbox is for current incoming mail, with reviewed mail filed into appropriate homes. Planner and document integration remain outside this release. Archive counts alone do not establish unwanted mail. Large inboxes use recent-mail coverage plus bounded historical groups, native search/aggregation, and separately approved deterministic backfills. Inbox zero is a direction, not permission for an installation-time sweep or a claim that archived historical mail was read. The README includes the supplied logo and the shared Agent Hands start marker.

## Recipient interface
Conversation owns setup, review, settings/history/restore, larger skill edits, connection repair, and errors. The agent owns all technical execution and presents effects and meaningful choices. Ordinary confirmations, ordinal selections, and readable titles map to exact private proposals. Workflow/access approvals record intent separately from implementation/provider completion. Code customization is prepared, checked, approved, installed, and verified by the agent, without assigning source editing or tests to the recipient.

## Remaining acceptance work

Test a known synthetic message and a uniquely named nonmatching rule only after their exact operations are approved. Verify durable state across a fresh chat and validate clean installation on that computer. Avoid claiming those checks from offline fixtures or another person's setup.
