# Agent Instructions
EmailButler is one self-contained package of focused skills under skills/. The docs/emailbutler.json manifest owns membership and version; the repository root is not a skill. Keep its person-facing workflow, connector setup guidance, typed configuration code, and required references together. Do not introduce a dependency on a separate toolkit or the author's private workspace.

## Product boundaries
The public Git repository is the sole distribution route. The README copy-paste prompt starts setup in the recipient's agent. That agent retrieves the repository, registers the skill, installs/enables the official requested connectors, and verifies its own environment. Keep connector sign-in, consent, and host-required approvals with the user. Do not add archive/upload distribution or preemptive work-laptop fallback flows.

The user interacts with an agent, not a terminal or source editor. Each focused skill owns its recipient-facing procedures, confirmations and recovery. The agent handles files, commands, runtimes, versioning, checks, request types, and diagnostics; recipient-facing explanations use outcomes and meaningful choices. Never forward helper output or ask the recipient to choose a path, revision, ID, code edit, or repair command. Reuse correct existing connectors and set up missing requested ones through the host's supported controls. Never silently replace a missing capability with browser automation, a new OAuth app, broader permissions, or a hosted service. Investigate actual restrictions when encountered. Developer-account probes do not verify a recipient's installation.

Preserve the exact durable-change entry phrase, typed change classes, preview/activation separation, and honest persistence reporting in skills/customize-emailbutler/SKILL.md and its guarded change contract. Human confirmation uses the readable current preview and natural replies or selections; short B labels are optional shortcuts. Keep technical proposal hashes internal; never require the user to copy or type them. A mailbox mutation is a separate operation from a local configuration change. Product permission boundaries cannot be changed through preference data. Approval of implementation/access requests is recorded separately from completion; the agent carries out the supported work and verifies it before claiming success.

Keep observations separate from approved settings. Persist only typed private evidence and checkpoints, never silently learn rules from counts or frustration. Default to 15 messages per text slate in the defined heading/link/recommendation/unsubscribe/separator format and two or three in voice. Check patterns proactively at completed slates without scheduling background work. Guide first-run cleanup toward specific folders/labels; stars, flags, and habitual Inbox storage do not create automatic Inbox exemptions. Preserve markers and honor explicit user overrides. Planner and document integrations are outside this release. Saved queue progress never carries mailbox approval into a new session.

## Development
Read README.md, docs/emailbutler.json, the relevant skills/*/SKILL.md and the active spike linked from TODO.md. Canonicalize registered skill paths to locate shared resources; install/update the complete package as a unit. Use installed global Project Workflows procedures when available; they are development aids, not package dependencies. Active spike records live in docs/active-spikes/. Make local coherent checkpoints; never push or add co-author trailers. Keep private profiles, credentials, email exports, and test-account evidence out of Git. Use synthetic fixtures.

Keep executable helpers and tests with their owning skills. Setup owns common registration/package validation and private-storage mechanics; Customize owns profile schema/defaults and guarded changes; Review owns queues/observations; Bulk owns filing checkpoints; Update owns migration decisions and their tests. Import shared mechanics from the owning skill without copying them or creating root script/test folders. Run `python3 -B skills/setup-emailbutler/scripts/run_tests.py` after changing scripts; `--skill NAME` runs one suite. Check idempotence and preservation of existing skills when changing installation. Record connector claims as documented, exposed, live-verified, unavailable, or unknown; never promote documentation or a tool name to a successful mailbox test. Keep platform-specific documentation in skills/setup-emailbutler/references/capabilities.md and recipient setup behavior in skills/setup-emailbutler/SKILL.md.

## Workflow ownership
Setup EmailButler registers a fresh collection or verifies correct registrations. Existing registration migration belongs to Update EmailButler: setup preserves the old registration and hands off, and only the update workflow requests the helper’s explicit migration mode after preparing the approved change. Setup then explicitly invokes Bulk Triage EmailButler for first-run or unfinished cleanup. Every selected account needs a recorded completed, user-deferred or blocked outcome before initial cleanup is reported as addressed; only verified completion is completed cleanup. Routine review checks this state. Bulk filing runs through the entire approved scope in bounded connector batches; review-slate boundaries do not end a bulk job. Private checkpoints preserve progress and returned IDs without carrying mailbox approval into a fresh session. An uncertain result must be reconciled before another write. The helper ledger makes no connector calls and cannot authenticate permission or force host execution.
